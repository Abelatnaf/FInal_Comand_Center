# Command Deck v3 — VMI Institutional Payment Tracker

## 0. What this is

A full ground-up rebuild, replacing the generic multi-tenant "Command Deck" (v2, below) entirely — same repo, same Supabase project, schema dropped a third time. Abel brought a complete, self-authored spec (`VMI Finance Command Center — v2` in his own doc, renamed **v3** here since "v2" was already taken twice in this project's history) and asked to keep discussing it before building; once he confirmed "this replaces everything" and then "let's get to building this," it was implemented directly against that spec.

This is a deliberate reversal of v2's own direction, not an oversight: v2 had generalized the app to be multi-tenant with open signup, cut all VMI-specific content, and added budgets/goals/an AI assistant. v3 walks all of that back — single user again, VMI-specific again, no chat assistant, no category budgets, no savings goals — in favor of a much narrower, harder-scoped tool: what's due to VMI, across two payers and two currencies, correct to the cent, usable on a phone with almost no time or connectivity. The full assumptions ledger, non-negotiable constraints, data model, currency rules, screens, design system, and build-order phases are Abel's own spec; only the deviations made while actually implementing it are recorded below.

**Real deadline context**: Abel's VMI matriculation date is 2026-08-15; this build started 2026-07-27, about 19 days out. The spec's own phase notes already account for this — Phase 1 ("the loop": `/add` + `Now`) is the minimum shippable product, and Phase 4 (offline/PWA) is explicitly called out as mattering more than Phase 3 (ledger polish) once he's actually at VMI with limited device access.

## 1. Non-negotiable constraints (Abel's spec, unchanged)

Thumb-reachable UI, a transaction logged in ≤10 seconds/≤3 taps, works offline (Phase 4), never lies about money (every USD figure traceable to a stored rate and date, no silent conversions), degrades rather than breaks, every entity has a delete path.

## 2. Currency rules — the reason this rebuild exists

Transactions are recorded in the currency they actually happened in; the FX rate is frozen at write time and never recomputed on edit unless the currency itself changes; historical totals never move when today's rate changes; only forward-looking estimates (coverage) use the current rate, and are visually marked with a `~` prefix and `.estimate` (muted) styling; the rate is entered manually in Settings — **no live FX fetch, ever**, a direct reversal of v2's `lib/fx.ts` (which called `open.er-api.com`/`exchangerate-api.com` automatically). This is the same class of bug this exact codebase has hit and fixed twice before (v1's `fix_fx_rate_lock_on_edit`, v2's `entries_direct_currency_entry`) — v3 designs the freeze into the database trigger from the start rather than patching it in later.

## 3. Data model — as built

Schema is Abel's `payers`/`accounts`/`fx_rates`/`obligations`/`transactions` design (all money `bigint` minor units, never floats), applied via `v3_full_reset_drop_everything` → `v3_schema` → `v3_grants` → `v3_seed` (mirroring the exact proven v1→v2 reset pattern, including the same grants gotcha: recreating `public` from scratch drops Supabase's default `anon`/`authenticated`/`service_role` table grants). `auth.users` is untouched by dropping the `public` schema, so Abel's existing login (`abelatnafu1@outlook.com`) carries over unchanged — no re-signup needed, and no public `/signup` route exists at all in v3 ("nobody else logs in" is now a hard constraint, not just a default). `cadet_weeks` (spec's own Phase 3, marked "if time allows") was not built.

**Deviations from the literal spec, and why:**
- **`obligations.status`/`is_past_due` are not stored columns.** The spec calls them "derived, stored for query speed," but at this app's real scale (one user, a handful of obligations) there's no query-speed case to make, and storing them would need trigger/cron machinery to keep in sync with both transaction changes and day-rollover — real complexity for zero benefit. Instead `obligation_progress` (a `security_invoker` view) computes `amount_paid_usd_minor`/`amount_remaining_usd_minor`/`status`/`is_past_due`/`days_until_due` live from `obligations` + linked `transactions`, every read, so there's no drift risk at all. The one thing that genuinely can't be derived — a bill being waived — is a real column, `obligations.waived_at`.
- **A currency/account-match trigger was added, not specified but implied.** `set_transaction_computed_fields()` (the same `BEFORE INSERT OR UPDATE` trigger that freezes the rate) also rejects a transaction whose `currency` doesn't match its `account_id`'s `currency`, since `balance_by_account` sums each account's transactions in that account's own native currency — a mismatched row would silently corrupt a balance. The Add/edit UIs prevent this by filtering the account picker to the selected currency, so this should never actually fire in normal use; it exists as a real database-level guarantee, not just a UI nicety.
- **No FX rate or obligations were seeded**, despite Phase 0's gate saying "seed... a starter account set, one FX rate." Fabricating an ETB/USD rate or a placeholder bill would itself violate "never lies about money" and section 6's own empty-state design (`"No obligations yet. Add the first VMI bill."`). Seeded instead: the two payers (`self` — Abel, Class of 2030; `family` — Class of 2029, label editable in Settings) and four starter accounts named directly from the spec's own examples (CBE, Cash ETB, US Checking, Payoneer), all at a $0/ETB0 opening balance for Abel to fill in for real.
- **Category chips are two fixed sets of 8, not one.** The spec says "a fixed row of 8, most-used first" without addressing that spending categories (Tuition & Fees, Food, Uniform & Gear, Personal Care, Travel & Leave, Transportation, Health, Other) and income sources (Freelance, Family Support, Stipend/Pay, Refund, Gift, Transfer In, Scholarship, Other) are obviously not the same set — `lib/categories.ts` keeps both, keyed by direction. "Most-used first" is computed from the real last-90-days transaction history, falling back to this default order for a new user with no history yet.
- **Verified `tsc --noEmit`/`npm run lint`/`npm run build` clean throughout** (15 routes) — required bumping `tsconfig.json`'s `target` from `ES2017` to `ES2022` (bigint literals like `10000n` aren't valid syntax below ES2020) and adding `allowImportingTsExtensions` (Node's native TS type-stripping test runner needs explicit `.ts` import extensions, which the bundler-mode resolver otherwise rejects).

## 4. Stack — as built

Next.js 16 (not the spec's "14" — this repo is already pinned to 16 with `proxy.ts`/async `params` per `AGENTS.md`; the spec's version number was drafting drift, not a real ask), Tailwind v4, Supabase, Zod (added — the spec's own mandate for "one source of truth per shape," used for the transaction schema shared between `/add` and edit), `date-fns` (added, spec's own mandate, `lib/date.ts`). **Auth is email/password, not the spec's "magic link"**: a magic link needs a timely inbound email at the exact moment of a rare, short, possibly-poor-connectivity session (assumption A1) — a worse fit than a password Abel already knows, which adds no live dependency to logging in at all.

Money/date helpers (`lib/money.ts`, `lib/date.ts`) have real unit tests — `npm test` runs Node's built-in test runner directly against the `.ts` sources (`node --experimental-strip-types --test`), zero test-framework dependency. 12 tests cover the round-trip, the exact rounding cases exercised in the live-DB rollback test below, negative-balance sign handling, and specifically that `convertToUsdMinor` is pure (calling it with a historical frozen rate gives the same answer regardless of what "today's" rate is elsewhere in scope) — the property that makes rate-freezing actually hold.

**Reused verbatim / lightly adapted** (schema/design-agnostic infra only, per "fresh components" — everything with UI or schema surface area was rebuilt clean): `lib/supabase/{client,server}.ts`, `components/ui/{HScroll,PullToRefresh}.tsx` (retinted off the removed Apple-HIG tokens), `ServiceWorkerRegister.tsx`, `InstallPrompt.tsx` (left as-is, not yet wired in — Phase 4), the PWA manifest/icon routes (retinted from iOS blue to the new monochrome-silver palette). **Removed entirely**: the AI Assistant (`lib/ai/`, `AssistantChat`, `ChatMarkdown`), Budgets, Goals, the old Transactions page + CSV bank-import flow, `QuickAddFab`, the `.glass` component and old Apple-HIG nav, `lib/format.ts` (superseded by `lib/money.ts`), `lib/fx.ts` (banned outright — no live FX fetch), the bubbly `DatePicker.tsx` (replaced with native `<input type="date">`, which fits the "cold, factual, no decoration" design system far better than a bubbly animated calendar ever would), the public `/signup` route and `AuthTabs`/`SignupForm`.

## 5. Design system — as built

Abel's monochrome-silver spec, implemented in full in `app/globals.css`: the exact token set (`--bg`/`--surface`/`--surface-raised`/`--border`/`--text`/`--text-muted`/`--text-faint`/`--silver`/`--urgent`/`--alarm`/`--positive`), Inter via `next/font/google` (the spec's "Inter or similar" — chosen over a system-font stack specifically because this app isn't Apple-only like several prior Command Deck design eras; a consistent look across whatever device Abel actually has on hand mattered more than platform-nativeness here), `tabular-nums` on every money value via `.num`, the `clamp(2.5rem, 12vw, 3.5rem)` weight-300 hero figure reserved for exactly one number per screen, 12px card radius / 8px control radius, 150ms motion respecting `prefers-reduced-motion`, and the `.estimate` (`~` prefix, muted color) treatment as the one honesty mechanism the whole app hangs on. No gradients, no blur, no glassmorphism — the deliberate opposite of this project's several prior design eras (Liquid Glass Monochrome, Neo-Luxury, Apple/iOS, light Apple-flare, Apple Wallet, Ethical Horizon), even though this is coincidentally the closest in spirit to the very first one.

## 6. Screens — as built

Four bottom tabs (Now/Add/Bills/Ledger) plus Settings behind an icon on Now, per spec.

- **`/` (Now)**: next-due obligation (title, payer, remaining, days-left — urgent under 14 days, alarm past due), a coverage line (`liquid_position` vs. next-due remaining, `.estimate`-styled), a compact balances list (`balance_by_account`), and the last 3 transactions via a shared `TransactionRow` component. Empty state when zero obligations exist at all (not just zero open ones) links straight to `/bills/new`.
- **`/add`**: amount keypad building a decimal string parsed through `lib/money.ts`'s `toMinor` (never a float), currency/direction segmented toggles, direction-appropriate category chips, a collapsed "More" (date/account/payer/note/obligation-link) defaulted sensibly (today, last-used account for that currency, default payer, no link) and auto-expanded when arriving via a Bills "Record a payment" link (`?obligation_id=&payer_id=`). A live `~$X.XX` preview renders under an ETB amount using the same fetched rate Now uses for coverage — display-only; the real frozen rate is computed by the database trigger at insert time, never by the client.
- **`/settings`**: FX rate entry (date/rate/source, upsert-on-conflict so correcting today's typed rate doesn't create a duplicate history row, a `>7 days` staleness warning per spec section 5), accounts CRUD (archive is the safe default delete path — `account_id`/`payer_id` on `transactions` are `on delete restrict`, so a real hard delete only succeeds on an account with zero history), payer label editing, JSON export, sign out.
- **`/bills`**: list (past-due pinned + loudest, via `status-pill`/`.progress-fill[data-alarm]`), `/bills/new`, `/bills/[id]` detail (progress bar, paid/remaining/total, "Record a payment" straight into a pre-filled/pre-linked `/add`, edit, waive/un-waive, delete).
- **`/ledger`**: reverse-chronological, filtered via plain `<form method="get">` query params (payer/currency/category-contains/date-range — no client JS needed for filtering, matching "URL params for filters"), a net-per-currency running total for the filtered set, CSV export (`lib/csv.ts`, trimmed of the now-unused CSV-import parser). Reuses the same `TransactionRow` as Now, so inline edit/delete (the one delete path required for every entity, section 2 rule 6) was built once and used in both places rather than twice.

**Not yet built, at this point in the build (matching the spec's own phase order)**: Phase 5 (resilience beyond the FX staleness warning — no read-only share link, no dedicated error boundaries yet). `cadet_weeks` (spec's Phase 3, explicitly optional) also not built. Phase 4 (offline/PWA) is done — see section 8. *Update: Phase 5 resilience (share links + error boundaries) was built in section 9; `cadet_weeks` was deliberately built as a scoped-down `settings`/`transactions_with_week` alternative rather than the literal spec table, also in section 9 — both left un-struck-through above so this reads as an accurate record of what was true at this point in the build, not the current state.*

## 7. Verification

A missing-rate insert and a currency/account-mismatch insert both raised the expected, human-readable errors. ## 8. Post-launch: Phase 4 — Offline / PWA

Asked what to build next; offered a menu (offline/PWA, resilience polish, cadet weeks) via `AskUserQuestion` since the spec's own "Do not add scope" list made guessing risky this close to Aug 15 — Abel picked offline/PWA, exactly the spec's own next-recommended phase.

- **Service worker** (`public/sw.js`) rewritten from a deliberate no-op into a real network-first, cache-as-fallback strategy for same-origin GET requests: every successful GET is cached under a versioned cache name, and a failed fetch (offline) falls back to whatever was last cached. `POST`s (Server Actions) are left completely untouched by the service worker — queuing a failed write is handled at the application layer (below), not by replaying an HTTP request the SW has no React context to construct correctly.
- **Cached reads, honestly marked stale**: rather than trying to track per-response cache provenance (real complexity for a single-user app), `OfflineBanner` just asks `navigator.onLine` — offline means "whatever's on screen predates this outage," full stop, shown via the same `.estimate` muted treatment already used for live-rate figures. Simpler than precise, and just as honest.
- **Queued writes**: `/add`'s submit is no longer a plain `<form action>` bound to `useActionState` — `AddForm` now calls `createTransaction` directly inside a manual `onSubmit`, checks `navigator.onLine` first, and on either "was already offline" or "network died mid-request," writes the entry into an IndexedDB queue (`lib/offline/db.ts`, `queue.ts` — a tiny hand-rolled wrapper, no dependency) instead of showing an error. This required changing `createTransaction` itself: it used to `redirect("/")` on success, which is right for an interactive submit but wrong for a silent background replay (it would force-navigate the browser mid-sync); it now returns `{success}` like every other action in this app, and `AddForm` navigates itself.
- **Sync indicator**: `SyncIndicator` (mounted in the app layout, so it's visible everywhere, not just Now) reads the IndexedDB queue on mount and on a custom `offline-queue-changed` event (dispatched by `queue.ts`, avoiding a poll), and auto-flushes (`lib/offline/sync.ts`, replaying each queued entry through the same `createTransaction`) the moment `navigator.onLine` flips true, with a manual "Sync now" fallback. A `flushingRef` guard prevents a re-render mid-flush from starting a second overlapping flush.
- **Install prompt wired up**: `InstallPrompt` existed but was never mounted anywhere — retinted off the old Apple-HIG tokens (`material`/`--separator`/`--blue`/`link-action`, none of which exist in v3's `globals.css`) onto the monochrome-silver tokens, then added to `app/(app)/layout.tsx`.
- **Verified with real browser tests, not just code review** — neither test below actually required live Supabase reachability (see section 7's correction: that was never confirmed this era, only assumed from a page that doesn't need live data to render). Installed `playwright-core` against the pre-installed Chromium (`npm install --no-save`, removed again afterward — never landed in `package.json`) and ran two real tests against a real `npm run dev` server: (1) loaded the public `/login` page online (static content, no live query needed), confirmed the service worker activates and takes control, went offline via `context.setOffline(true)`, reloaded, and confirmed identical real content was served from cache rather than a browser error page; (2) a temporary route (`app/dev-test-queue`, briefly allow-listed in `proxy.ts`, both fully deleted/reverted afterward — confirmed via `git status` showing neither) exercised the actual shipped `lib/offline/queue.ts` against a real IndexedDB (pure client-side, no Supabase call at all), confirming enqueue/list/remove round-trip correctly. The AddForm/SyncIndicator/OfflineBanner UI itself, wired to real authenticated data, couldn't be click-tested for the same standing password-access reason — verified by code review instead.
- `tsc --noEmit`/`npm run lint`/`npm run build` clean throughout (still 15 routes — this was all changes to existing routes, no new pages); `npm test` still 12/12 (unaffected).

## 9. Post-launch: weekly windows + Phase 5 resilience

Asked what to build next again; offered the two remaining unbuilt spec items via `AskUserQuestion` (Phase 5 resilience, cadet weeks) since Phase 0–4 were now all done — Abel picked both. Mid-turn, Abel separately said not to make the app VMI-specific.

- **Genericized existing VMI-specific copy** (found via a grep sweep, three hits): Now/Bills' empty-state button ("Add the first VMI bill" → "Add the first bill" in both places) and a line in `/terms` ("VMI billing statements" → "billing statements"). Per this project's own established precedent (see the "Branding genericized" entry under Command Deck v1 below), only *live app copy* was touched — this file's historical prose, and Abel's own real seed data (payer labels like "Class of 2030," account names like CBE/Payoneer), stay as they are, since those are accurate facts about the one real user, not generic-app copy.
- **"Cadet weeks" was deliberately not built as such** — the spec's own `cadet_weeks` table (`week_number`, `starts_on`/`ends_on`, `allowance_usd_minor`) was scoped down for two reasons, one pre-dating and one following from the genericization ask: (1) v3 explicitly cut budgets — a stored per-week *allowance* with a spent-vs-allowance comparison UI would quietly reintroduce exactly what was cut; (2) "cadet" is itself VMI-specific naming. Built instead: a minimal `settings` table (`tracking_start_date`, generically named even though its one real value is Abel's actual matriculation date) and a `transactions_with_week` view computing `week_number` live from `occurred_on` — never stored, no trigger involved, since it only depends on a transaction's own date plus a start date that essentially never changes, so there's no drift risk either way and it stays out of the money-critical transactions trigger entirely. Surfaced as a `Week #` filter on `/ledger` (alongside the existing payer/currency/category/date filters) and each row's subtitle, plus a small `Week N` label next to the Now heading — deliberately not a dashboard, matching "no charts, no dashboards."
- **Read-only share links** (`share_links` table + `get_shared_snapshot(p_token)`): a 192-bit hex token (unguessable, not a sequential id), revocable, listable/creatable from a new Settings card. The function is `security definer` specifically so an anonymous visitor — who has no `auth.uid()` and would otherwise be blocked by RLS on every table involved — can resolve a token to its owner and read a narrow, explicit, `v_user_id`-scoped snapshot (next-due obligation, coverage, balances). Deliberately excludes the transaction list/notes: a share link answers "is this covered," not a window into every purchase. New public route `/share/[token]` (added to `proxy.ts`'s public allowlist) renders it as a stripped-down mirror of Now, with a distinct "couldn't load, try again" state kept separate from "this link isn't valid" — conflating a transient fetch failure with a genuinely revoked link would misreport a real link as dead.
- **Error boundaries**: `app/(app)/error.tsx` (a plain "something went wrong, nothing you've saved is affected" plus Try again / Back to Now) and a root `app/error.tsx` for errors outside the authenticated app group (login, legal pages, the new share page) — matching "degrades, not breaks" as one of the non-negotiable constraints.
- **Caught and fixed two real mistakes before they shipped, not after**: (1) `get_shared_snapshot`'s underlying views promote money columns to `numeric` via `sum()`/`round()`, not `bigint` as declared — the very first rollback-only test against the live database failed with a type-mismatch error, fixed by casting explicitly on the way out; (2) while fixing that, the same edit accidentally flipped the function from `security definer` to `security invoker`, which would have silently made the whole feature non-functional for anonymous visitors (RLS would block token lookup entirely) without erroring — caught by a second rollback-only test that specifically ran the function `set local role anon` and got `found: false` for a token confirmed valid moments earlier under the normal role. Both are recorded as their own migrations (`fix_shared_snapshot_numeric_cast`, `fix_shared_snapshot_security_definer`) rather than silently folded into the original, matching this project's "raw SQL is an honest record" discipline.
- **`get_advisors` correctly flags `get_shared_snapshot` as anon/authenticated-executable `security definer`** — confirmed expected, not remediated, since exactly that is the feature. The one pre-existing dashboard-only item (leaked-password-protection) is the only other finding.
- **A live end-to-end test of the actual `/share/[token]` page was attempted, and its failure is what surfaced the section 7/8 correction above**: created one real (not rollback) `share_links` row, hit the page through a real `npm run dev` server, and got "this link isn't valid" for a token confirmed valid by direct SQL — traced to the genuine egress block (`$HTTPS_PROXY/__agentproxy/status` showed `connect_rejected`/403 for the Supabase host), not a bug in the function or the page. Fixed the page to distinguish that failure mode honestly (see above) rather than leaving "not valid" to cover both cases, then deleted the real test row (`delete ... returning id`, confirmed) and the standalone debug script used to isolate the cause.
- Verified: the two DB-level rollback-only tests above (schema/type correctness, anon-role scoping including the security-definer regression); `tsc --noEmit`/`npm run lint`/`npm run build` clean (16 routes, up from 15 — `/share/[token]` is new); `npm test` still 12/12. The live page render, the Settings share-link create/revoke UI, and the Ledger week filter against real data could not be click-tested this session for the now-confirmed egress reason — verified by code review instead.

## 10. Post-launch: obligation duplication

**Receipt photos** (`lib/receipts.ts`, `components/money/ReceiptLink.tsx`): a `receipt_path` column plus upload on `/add` and attach/replace in the Ledger edit row. Deliberate choices: the upload happens *after* the transaction row exists, so the path can be `<user_id>/<transaction_id>/receipt.<ext>` (the shape the existing policies key off); a failed upload reports itself but does **not** fail the entry, since the money is already recorded correctly and losing a transaction over a missing attachment is the worse outcome; viewing mints a fresh 60-second signed URL per click rather than storing a link, so there's no durable URL to leak from a private bucket; and the user's own filename is discarded (only the extension is kept) because it can contain characters the storage path rejects. The offline queue only carries string fields, so attaching a receipt while offline would have silently lost it; `/add` now says so explicitly instead.

**Installments** (`obligation_installments` + `installment_progress` view): a *plan*, not a second ledger. Payments still link to the obligation as a whole, and which part is settled/next/overdue is derived every read from cumulative amounts versus what's actually been paid — so a plan edit can never contradict the ledger, and there's no sync machinery to drift. Same reasoning that kept `obligations.status` derived in the first place. Money columns are cast back to `bigint` on the way out of the view, since `obligation_progress` promotes them to `numeric` via `sum()` — the exact mismatch that broke `get_shared_snapshot`'s first version. Surfaced as a plan editor on the bill detail page and a "Next part" line on Now, which is usually the smaller, more actionable number than the full remaining balance. The plan total is compared against the bill total but deliberately **not** enforced — a plan that intentionally covers part of a bill is legitimate.

**Recurring bills** (`recur_interval_months` + `recur_spawned_at` + a daily `pg_cron` job): the next copy is created automatically once a bill's due date passes. `recur_spawned_at` is the double-spawn guard (same dedupe shape as v1's `last_posted_date`), and each loop iteration has its own exception block — an uncaught error inside a plpgsql loop aborts the whole call, which is exactly how v1's recurring auto-post once silently stopped every user's bills because of one bad row. A repeat is anchored to the due date, so the UI says so when one isn't set rather than letting the setting quietly do nothing.

**Safe backup restore** — the feature explicitly deferred in section 12, now built properly. The hard part: `set_transaction_computed_fields()` looks up the *latest* rate on INSERT, so replaying a historical ETB row would silently reprice it at today's rate. Solved with a narrow **role-gated escape hatch**: the trigger honours a caller-supplied rate only when `current_user = 'postgres'`. A PostgREST client is always `anon`/`authenticated`/`service_role` and can never become `postgres`, so the guarantee still holds on every path a client can reach; inside a `SECURITY DEFINER` function owned by `postgres`, `current_user` *is* `postgres`, which is what lets `restore_from_backup()` write history faithfully. The restore is one atomic database function (a half-applied restore would be worse than none) and writes every row under `auth.uid()`, **never** the payload's `user_id` — it's `SECURITY DEFINER`, so RLS doesn't protect it and trusting a supplied `user_id` would let anyone overwrite another user's data. `exportAllData` also gained `obligation_installments`, since an export that omits a table restore reads is a broken backup.

## 14. Post-launch: transfers, duplicate detection, Bills filters, pay-remaining

Asked for "WAY MORE FEATURES" -- the fourth such ask in a row, and previous open-ended questions had come back non-specific, so this batch was picked from real gaps rather than by asking again.

**Transfers between accounts** (`transfers` table) -- the biggest genuine hole in a two-currency app. Moving money between your own accounts had no representation at all, so the only way to record a USD -> ETB move was a fake expense plus a fake income, which inflates both totals and corrupts every category, ledger and coverage figure derived from them. v1 had transfers; v3 dropped them and never replaced them.
- **Both sides of the amount are stored explicitly** (`from_amount_minor` / `to_amount_minor`) rather than deriving one from the other via a rate. For a cross-currency move those are two independent facts -- what left and what arrived -- and any spread or fee is simply the visible difference. Inferring one from a rate would be inventing a number, which is the thing this app exists not to do. Equal amounts are *not* enforced, since a wire fee legitimately makes them differ.
- `balance_by_account` was rewritten with scalar subqueries instead of joins: joining both `transactions` and `transfers` fans out the rows and double-counts the sums. `liquid_position` had to be dropped and rebuilt around it (it reads that view), though its own definition is unchanged.
- Transfers live in their own table, so every income/spending view ignores them for free -- no filtering to remember and get wrong later.

**Duplicate detection on `/add`** -- v1 and v2 both had this; v3 lost it. Warns (never blocks) when an identical date/amount/currency/direction/account entry already exists, and the second submit carries a confirm flag through. Deliberately a warning: logging the same coffee twice in a day is real, but silently double-recording a bill payment is costly.

**Bills filters** -- the Ledger had seven filters and Bills had none. Added search, payer and status filters, three sorts, a "still owed" total for the filtered set (with past-due called out separately), and CSV export. Filtering happens in the page rather than the query because `obligation_progress` derives `status`/`is_past_due` at read time -- they aren't columns the database can filter on.

**Pay-remaining shortcut** -- one tap from a bill into `/add` prefilled with the exact outstanding figure, instead of reading the number off the screen and retyping it. Only offered when something is actually outstanding.

**A gap this batch created and closed in the same pass**: adding `transfers` without teaching `restore_from_backup` about it would have made every backup silently lossy -- export/restore would wipe transfer history and leave balances wrong. `exportAllData`, the restore function, and the restore preview all learned about transfers, and the FK-safe delete order was updated (transfers reference accounts with `on delete restrict`, so they must be cleared first).

- **Transfers**: exact deltas on both sides of a cross-currency move, no transaction rows created, liquid position consistent, deletion fully reverses, same-account and zero-amount refused, and an account with transfer history can't be deleted.

- **Rename an account.** Accounts could be added, rebalanced, archived and deleted, but not renamed. Currency deliberately stays uneditable: an account's transactions are stored in its currency and the database enforces the match, so changing it would either fail outright or silently misrepresent history -- the UI says to make a new account instead.
- **Add and delete payers.** `PayersForm` only edited labels, so the two seeded payers were permanent and a third (a sponsor, a scholarship) was impossible -- a real limitation once the app was genericized away from being VMI-only. `key` is unique per user and is only an internal handle, so it's derived from the label and disambiguated with a numeric suffix rather than being asked for. Delete is hidden when only one payer remains, since every transaction and bill requires one and deleting the last would make the app unusable. `payer_id` is `on delete restrict` on both `transactions` and `obligations`, so deleting one with history raises -- caught and reported as plain guidance rather than a raw constraint error.
- **Edit a transfer.** Previously create/delete only, so fixing a typo meant deleting and re-entering. Worth noting this is safe in a way editing a *transaction* is not: a transfer stores both real amounts rather than deriving either from a rate, so there is no frozen-rate concern -- editing one is just correcting a recorded fact.
- **Attach a statement to a bill.** Receipts proved a payment was made; nothing held the bill itself, which is the document you'd actually need to query a charge. `obligations.statement_path` reuses the existing private `receipts` bucket under `<user_id>/obligations/<id>/...` -- its policies key off the first path segment being `auth.uid()`, so this needed no new storage rules at all.

**Verified**: `tsc --noEmit`/`npm run lint`/`npm run build` clean (18 routes); `npm test` 12/12. One rollback-only test, zero residue: an unused payer deletes cleanly; a payer used by a transaction and one used by a bill are both correctly refused; a duplicate payer key is refused (confirming the add action genuinely has to disambiguate rather than hoping); renaming an account leaves its balance and its transactions untouched; and `statement_path` round-trips.

**Follow-up, from checking the live account's actual state rather than assuming**: it had two active ETB accounts and **zero** FX rates, which meant every ETB entry would be rejected on submit with no prior warning anywhere. Now's coverage line is the only place that mentions the rate, and it only renders when a next-due bill exists -- there were no bills, so nothing surfaced it. Same class of problem as the `/add` screenshot in section 12, reached from a different direction. Added `FxRateNotice` on Now, which appears **only** when something is actionable: no rate at all while ETB accounts exist, or a rate past the same 7-day staleness threshold the Settings form already uses (reusing `isOlderThanDays` rather than restating it). A current rate, or no ETB accounts, renders nothing -- a banner that's always present stops being read. The stale copy is careful to say recorded entries keep the rate they were saved with and it's the *coverage estimate* that drifts, since the opposite reading would contradict the whole freezing design. Verified `tsc`/lint/build/test clean and screenshotted both states against the real compiled CSS.

**Deliberately not built**: due-date push notifications, which is the obvious remaining gap. Web Push needs a push service, VAPID keys and a send-side backend -- real infrastructure plus keys only Abel can supply, so scaffolding it here would produce something non-functional rather than a feature. Called out rather than quietly skipped.

## 17. Post-launch: the expense-tracker redesign ("v4")

Abel asked to "completely redesign it — a finance tracker with all the important features, because I want to use this website to track ALL my expenses." That is a genuine change of purpose, not a reskin: v3 was built around *what do I owe* (Now/Add/Bills/Ledger, bills on the front page), and an everyday expense tracker is built around *where is my money going*.

**Not another ground-up rebuild.** This project has dropped its schema three times, and each rebuild re-lost hard-won correctness work — the FX-freeze bug class alone has now been fixed three separate times. The live data was near-empty (2 transactions, 4 accounts, 0 bills/transfers/rates), so a reshape was cheap either way, but the money core (minor-unit bigints, the write-time rate freeze and its role-gated restore escape hatch, transfers, receipts, the offline queue, backup/restore) was kept and extended rather than re-derived. Only the parts that were actually wrong for the new purpose changed. Hence "v4" in the migration names but no `drop schema` — v3's sections above still describe the live system except where contradicted here.

**Four standing constraints were deliberately overridden, on Abel's explicit call** (asked before building, via `AskUserQuestion`, because each contradicts something this file already committed to): v3 cut category budgets, banned charts and dashboards outright, cut savings goals, and — since section 11 — locked the app to dark-only. All four are now reversed. He also picked "full expense tracker, keep bills" over dropping bills entirely, and "modern fintech, light + dark" over evolving the dark Premium look. Recorded as an informed reversal, not an oversight.

**Schema (six migrations, all mirrored into `supabase/migrations/`):**
- **`categories` is a real table**, replacing the hardcoded 8-label lists in `lib/categories.ts` and the bare `transactions.category` text column. That column was the blocker for budgets: there was nowhere to hang one. Carries `monthly_budget_usd_minor`, a colour token and an icon. Seeded with a general-purpose everyday set (Groceries/Dining Out/Transport/… , Salary/Freelance/…) rather than v3's tuition-and-uniform set.
- **`transactions.category_id` FK**, replacing the text column. Chosen over text-linking specifically so **renaming a category can't orphan history** — a normal thing users do that must not corrupt years of data. The reverse risk (deleting a category nulls its transactions) is handled by making archiving the offered path and hard delete only succeed when nothing references it, mirroring how accounts already behave here. Existing labels were folded into real categories before the backfill so nothing was dropped.
- **`recurring_expenses`** deliberately stores **no currency of its own** — the charge happens in its account's currency, and transactions already enforce currency-matches-account at the database level, so deriving it removes the mismatch class entirely instead of adding a second constraint to keep in sync. `post_due_recurring_expenses()` is a daily `pg_cron` job that **catches up a whole backlog in one run** (an inner loop, guarded at 120 iterations) rather than one occurrence per day, and gives **each row its own exception block** — an uncaught error inside a plpgsql loop aborts the entire call, which is exactly how v1 once silently skipped every user's recurring posts because of one bad row.
- **`savings_goals`** + a `savings_goal_progress` view: a linked goal reads its account's live balance, an unlinked one uses a manual figure, derived every read so a linked goal can't drift. A linked goal is required to match its account's currency, since progress is read straight off that balance and a mismatch would silently compare two different units.
- **Three analytics views** — `budget_status`, `monthly_summary`, `category_spend_by_month` — all derived every read (no stored aggregates, no sync machinery, consistent with why `obligations.status` was left derived in the first place). All measured in `amount_usd_minor`, each transaction's own frozen figure, so **every number on the budgets and insights screens is immune to today's rate moving** — which is why none of them needed `.estimate` marking.
- **`restore_from_backup` and `exportAllData` learned all three new tables plus `category_id`** in the same pass. Skipping that would have made every backup taken from this point silently lossy — wiping categories/recurring/goals and stripping every transaction's category on restore. Same gap this project already closed once for transfers in section 14.

**Design: light + dark, both selected rather than one flipped from the other.** `app/globals.css` rewritten around an indigo accent with real semantic income/expense colour (emerald/rose — direction is the thing you scan for in an expense tracker). Light is the default case for the first time in this project's history, because an everyday tracker gets opened outdoors constantly. Dark values are their own steps chosen for a dark surface, declared under both the OS media query and an explicit `data-theme` stamp so a manual toggle can win in either direction.

**Contrast was computed, not eyeballed** — this project has shipped this exact bug class twice (v1 Phase 8's `text-faint` at 2.18:1; section 11's Dark Premium palette reintroducing it at 3.12:1). Ran the real WCAG formula over every functional pairing in both modes and found **three real light-mode failures**, all fixed before shipping: `--text-faint` at 4.28:1 on the page and 4.03:1 on the inset surface (→ `#646e7e`, clears 4.5:1 on all three surfaces); `--urgent` at 4.40:1 on the inset surface (→ `#b05109`); and — the one that needed its own fix rather than a token change — **the "partial" status pill at 4.41:1, because it puts `--urgent` text on a tint of its own colour**, so brightening the text also brightens its background and drags the pair back under. Fixed by dropping that tint from 12% to 8% (4.67:1). Exactly the self-referential-pill trap section 11 hit with "waived". All 12 category colours clear 3:1 as bar fills in both modes.

**Charts, built to the `dataviz` skill's rules, with no charting dependency:** ranked **horizontal bars with direct name-and-figure labels** for the category breakdown — deliberately not a pie or donut, so identity never rests on colour alone and the CVD constraints that cap a categorical palette at ~8 slots stop being load-bearing; a **single-series column chart** for the month trend (no legend — the heading names it; only the peak is directly labelled; every column carries a native `title` so an exact figure is one press away without shipping a client component). Colour follows the **category**, never its rank, so filtering never repaints the survivors, and anything past the cut folds into one "Other" bar rather than generating new hues. No dual-axis anywhere.

**Screens** — five tabs (Home/Ledger/**Add** raised in the centre/Budgets/More) plus `/more` for Insights, Bills, Recurring, Goals, Upcoming, Settings. Home is now spending-first: this month's spend as the hero with a real month-over-month delta, the trend chart, budget progress, where-it-went, accounts, then next bill demoted to one compact row. New `/budgets` (inline budget editing, budgeted first then unbudgeted ranked by actual spend — the most useful order for deciding what to budget next), `/insights` (month selector, biggest movers vs. the prior month, month-by-month table; averages only over months with real activity, since dividing by twelve on two months of history would understate badly), `/recurring` (monthly burn grouped **by currency rather than converted**, because converting would be an estimate at today's rate rather than a fact), `/goals`, `/more`. Ledger rows now lead with the note (what identifies a purchase) over the category (how it's grouped), and the category filter became a real picker instead of a substring match.

**Verified**: `tsc --noEmit`/`npm run lint`/`npm run build` clean throughout (**22 routes**, up from 18); `npm test` 12/12. A 12-check rollback-only test against the live database covered budget scoping to the current month, last-month isolation, per-category-per-month splitting, a **three-month recurring backlog caught up in a single run (4 posts)**, a rerun posting **zero** (the double-charge guard held), and linked-vs-manual goal progress — zero residue. The one FAIL in that run was **my test's expectation, not the view**: `monthly_summary` sums the whole month and Abel's real $5.00 entry from 2026-07-30 sits in it, so 4000+500=4500 was correct — the same stale-baseline mistake section 14 records. `get_advisors` (security) shows only the three known intentional items; `post_due_recurring_expenses` is correctly **not** flagged, confirming its revoke held. Real browser verification in **both themes**: `/login` screenshotted against a freshly-compiled dev server (with `.next` cleared first — section 11 bug #3 is that a freshly-started `next dev` is not proof of freshly-compiled CSS), asserting `--bg`/`--accent`/`--cat-emerald` resolve to the new values rather than trusting the diff; and a harness built from the **real compiled stylesheet** (fetched off the running server, not hand-approximated) rendering every new surface — hero, trend chart, ranked bars, budget rows in normal and over-budget states, transaction rows, goal card, recurring item, all five status pills, controls, keypad and the new tab bar — screenshotted light and dark. The authenticated pages against real data still can't be click-tested for the standing egress reason (outbound HTTPS to the Supabase host is blocked from this sandbox); those were verified by code review plus the database tests above.

**Also swept**: `text-silver` (a class this redesign removed) was still live in six files — replaced with `text-accent` rather than left to silently render as body text; the PWA manifest and all three icon routes were retinted off the removed emerald/near-black palette; `/login`'s tagline still said "What's due, and what covers it," which is the old bill-tracker's promise, not this one's.


## 18. Post-launch: "v5" — a US, USD-only expense tracker anyone can sign up for

Abel asked to "add as many features as we can and make it only used for US and the general public... i dont want it only for me." Two of the three implied changes are destructive, so all three were confirmed via one `AskUserQuestion` round before anything was applied: **remove the ETB/exchange-rate system entirely (USD only)**, **remove payers entirely**, and **fully open signup**. All three came back as the recommended option. Checked first rather than assumed: the live account held 2 transactions (both USD, both at the placeholder rate 1.0) and 2 ETB accounts with zero balance and zero history, so going USD-only cost no real data.

**The FX system is gone, not hidden.** `fx_rates`, `transactions.fx_rate_etb_per_usd`, `transactions.currency`, `accounts.currency`, `savings_goals.currency` and the two-sided `transfers` amount all dropped. `transactions.amount_usd_minor` went with them — with one currency it was byte-for-byte `amount_minor`, so keeping both would have been duplicated state; the views keep their `_usd_minor` output names (still accurate, every figure is dollars) so downstream consumers didn't have to be renamed. **The role-gated restore escape hatch went too**: `restore_from_backup` needed `current_user = 'postgres'` to write a historical frozen rate faithfully, and with no rate to freeze there is nothing to reprice, so that mechanism was deleted rather than carried forward. This retires a bug class this codebase had fixed four separate times.

**Payers are gone**, taking a required field off every entry, a filter off Ledger and Bills, a picker off Add and Recurring, and a settings card with it.

**A real cross-tenant write hole, found by thinking about what open signup changes.** RLS checks a row's own `user_id`; it does **not** check that the `account_id` the row points at belongs to the same person, and a foreign key only requires the target to exist. With one user that was harmless. With open signup, anyone who learned another user's account uuid could have inserted a transaction into their balance. Closed with `assert_owned()` plus per-table `BEFORE INSERT OR UPDATE` triggers on transactions, transfers, recurring expenses, savings goals and installments. Verified by trying it: as user B, inserting against user A's account is refused with "Account not found", and so is a cross-tenant transfer.

**Signup, and everything a public app owes its users**: `/signup`, `/forgot-password`, `/reset-password`, and `/auth/confirm` (a route handler that exchanges the emailed token before any page renders, so the destination never flashes signed-out — and only ever redirects to a same-origin path, since taking the raw `next` parameter would turn every confirmation email into an open redirect). A `handle_new_user()` trigger provisions each signup with a settings row, three accounts and 26 categories — without it a new user would land in an app where the first entry is impossible, since a transaction requires an account. A three-step `/welcome` wizard (name, accounts + real balances, a couple of budgets) runs once, gated on `settings.onboarding_completed`; the app layout reads the current path from a header the proxy now sets, so `/welcome` doesn't redirect to itself. Self-serve **account deletion** (`delete_own_account()`, type-DELETE-to-confirm) and the existing JSON export cover taking your data and leaving. The reply to a password-reset request is deliberately identical whether or not the email exists — otherwise the form is an account-enumeration oracle.

**Nine features, picked as the gaps that matter for an everyday US tracker:**
- **Credit cards as first-class liabilities.** `accounts.kind` now describes real US account types (checking/savings/cash/credit/investment/other) with `institution` and `credit_limit_minor`. A card's balance goes negative as you spend, so **net worth is a plain sum** — no sign gymnastics anywhere.
- **`/net-worth`**, with a `net_worth_by_month` view. Transfers between your own accounts never move net worth, so the view only walks transactions — which is also why it can't drift. The chart baselines at **zero rather than the minimum**: a bar growing downward is the honest picture of debt, where a floor at the lowest value would make it look like progress. Credit utilisation is shown against the limit, flagged past the 30% mark.
- **Auto-categorisation rules** (`category_rules`), applied **in the database trigger, not the app**. That was the deciding call: rules in one server action would have silently skipped CSV import, the recurring-expense cron job and the offline-queue replay. An explicitly chosen category always wins over a rule, and a rule only matches a category of the right kind (an expense rule can't file income). "Apply to uncategorized" back-fills history, since rules otherwise only fire on write.
- **CSV import from US banks** (`/import`, `lib/bank-csv.ts`) — hand-rolled, no dependency. The parts that actually break on real files are the bank quirks, not the RFC-4180 core: a summary preamble above the real header (Bank of America), different header names between checking and card exports ("Posted Date"/"Payee" vs "Date"/"Description"), separate Debit/Credit columns, `(45.20)` parentheses negatives, `$1,234.56`, `MM/DD/YY`, and Excel's BOM. `parseBankDate` returns null rather than guessing, because a misread date silently files a purchase in the wrong month. Sign convention is a visible toggle with a live preview, not an inference. Re-importing an overlapping statement is safe: same date + amount + direction + account is skipped, including duplicates *within* the file.
- **Tags** on transactions, with a Ledger filter — they cut across categories (a trip, a client, a reimbursement) in a way one category can't.
- **Tax-deductible flag** plus a year-end summary, worded carefully as a record of what you marked rather than a judgement about what qualifies.
- **`/reports`** — year in review: totals, savings rate, biggest month and category, month-by-month, and the deductible list. Averages divide by **months with real activity**, since dividing by twelve on three months of history understates badly.
- **Bill reminders on Home** — a 14-day "coming up" list merging obligations *and* recurring charges, since a reminder that only covers hand-entered bills isn't one.
- **Merchant autocomplete** on `/add`, ordered by how often each description repeats.

**Two real bugs fixed on the way, neither one the thing being worked on:**
1. **The offline queue silently dropped duplicate-looking entries.** `flushQueue` only removed an entry when the action returned no `error` — but the duplicate guard returns `{duplicateWarning: true}` with no error, so a replayed entry that looked like a duplicate was deleted from the queue *without ever being saved*. A replay is never a double-tap, so it now always carries `confirm_duplicate`.
2. **`Date.now()` in a server component**, caught by the React purity lint rather than at runtime; replaced with a `daysAheadIso` helper alongside the existing `daysAgoIso`.

**Verified**: `tsc --noEmit`/`npm run lint`/`npm run build` clean (**31 routes**, up from 22); `npm test` **24/24**, up from 12 — the new bank-CSV parser got 14 of its own covering the preamble skip, both header shapes, split debit/credit columns, every amount and date format above, and the flip-sign toggle. Two rollback-only tests against the live database, zero residue confirmed each time: **11 checks** on provisioning, the cross-tenant write and transfer refusals, rule matching (including that an explicit category wins and that kind is respected), same-account transfer refusal, and the balance/liquid/debt/net-worth arithmetic reconciling exactly; then **9 checks** on tags and the tax flag round-tripping through a full export→wipe→restore cycle with the credit account and its limit intact, and `delete_own_account` leaving zero rows across every table plus `auth.users`. One inline "want" annotation in the first test was a stale guess written before a third transaction was added to the fixture — the balances were right, the annotation wasn't, the same mistake sections 14 and 17 already record. `get_advisors` (security) shows only the three intentional `security definer` functions and the one dashboard-only item; `handle_new_user` is correctly **not** flagged, confirming its revoke held. Performance advisors show only INFO unused-index items on tables that have almost no data yet.

**Flagged for Abel, not fixable from here**: Supabase's **leaked-password protection is still off**. It was a minor note when one person had an account; with open signup it is the single most valuable remaining setting, and it's a dashboard toggle (Authentication → Policies) no migration can flip. Same for whether email confirmation is required on signup — the code handles both cases rather than assuming either.

**Real browser verification, and it caught a contrast bug.** `/login`, `/signup` and `/forgot-password` are reachable without live data, so those were screenshotted against a freshly-compiled dev server in **both themes**, asserting `--bg`/`--accent`/`--alarm` resolve to the new values rather than trusting the diff (section 11 bug #3: a freshly-started `next dev` is not proof of freshly-compiled CSS, so `.next` was cleared first). For the authenticated surfaces this sandbox can't log into, a harness built from the **real compiled stylesheet fetched off the running server** rendered every new surface — the net-worth hero, both chart states, credit utilisation, the due-soon list, a tagged ledger row, the import direction check, an onboarding step and the year-in-review rows — screenshotted light and dark. Two things came out of actually rendering it:
- **`NetWorthTrend`'s zero line was verified numerically, not by eye.** Measured every bar's geometry: with debt present, each debt bar starts at exactly the midline (60 of 120px) and grows down while each asset bar ends at exactly the midline and grows up; with no debt the baseline is the bottom of the chart and the full height is used. The fixed zero line holds.
- **A real contrast failure in the new chart, found by sampling painted pixels.** Prior months were dimmed to `opacity: 0.55`, which composites to **2.85:1 (light) / 2.79:1 (dark)** against the card surface — under the 3:1 floor for meaningful graphical objects, and these bars *are* the data. Solved for the smallest alpha clearing 3:1 in all four theme/colour combinations rather than guessing: **0.7** (3.4–3.9:1), re-measured from real pixels after the change. This is the fourth time this project has shipped a contrast bug (v1 Phase 8, section 11, section 17) and the first time it was caught before the commit rather than after.

**Immediate follow-up: the ownership triggers broke every write in production, and the tests said they were fine.** Abel hit `permission denied for function assert_owned` trying to save an entry — the app could not record a single transaction, transfer, recurring expense, savings goal or installment. `assert_owned` is deliberately revoked from `anon`/`authenticated` so a client can't call it as an ownership oracle, but the five trigger functions calling it were `SECURITY INVOKER`, so they executed **as the signed-in user**, who has no `EXECUTE` on it. Fixed by making the trigger functions `SECURITY DEFINER` (they then run as the owner, which can call the helper) rather than by granting `EXECUTE` — the helper stays unreachable from PostgREST, and the triggers only read a `user_id` and either raise or set a category, with every lookup explicitly scoped to `new.user_id`.

**The real lesson is about the test, not the code.** The original 11-check test asserted "cross-tenant write refused" and passed — but it ran over the MCP connection as `postgres`, where `assert_owned` *is* executable, so it exercised a code path no real user can reach. A permissions test that doesn't `set local role authenticated` proves nothing about permissions. The fix was verified by first **reproducing the failure** as `authenticated`, then re-running six checks in that role: saving a transaction works, the auto-categorisation rule still fires inside the same trigger, a forged cross-tenant `user_id` is still refused with "Account not found", transfers save, same-account transfers are still refused, and a savings goal saves. `get_advisors` is unchanged — the five now-definer functions are correctly **not** flagged, confirming their revokes held.

**Standing limitation, unchanged**: outbound HTTPS to the Supabase host is blocked from this sandbox, so the authenticated screens against real data still can't be click-tested here. Correctness was verified at the database layer with the rollback tests above and by code review; the money helpers and the CSV parser are covered by real unit tests.

# Command Deck v2 — Build Spec

## 0. What this is
A personal finance web app, rebuilt from scratch as a deliberately small, Apple-designed tool. The original app (documented in the Build Log below, kept for history) grew to ~27 routes across many incremental sessions — MFA, month-end close, tax reports, forecasting, audit log, multi-currency, backups, CSV import, and more. Abel asked to "completely change the whole script": a full ground-up rebuild, not another reskin, driven by two things — the app had gotten too complex, and none of the seven prior visual redesigns (all documented below) actually felt right. This version starts over with a hard constraint on scope (5 pages, one unified ledger table) and a real, HIG-accurate Apple design language rather than an approximation of one.

This was a genuine fresh start: the previous Supabase schema (17 tables), all 3 pg_cron jobs, and all 3 real signed-up `auth.users` rows (including Abel's own account and its data) were dropped/deleted as part of this rebuild, with Abel's explicit confirmation that this loss was acceptable.

## 1. Stack
Unchanged from v1 — nothing about the stack was the problem, only complexity and design.
- **Framework:** Next.js 16 (App Router), TypeScript — `proxy.ts` (not `middleware.ts`), exported function name `proxy`. `cookies()`/`headers()`/`params`/`searchParams` are all async.
- **Styling:** Tailwind CSS v4 (CSS-first config, no `tailwind.config.js`)
- **DB/Auth:** Supabase (Postgres + Supabase Auth, email/password, open signup — multi-tenant)
- **Hosting:** Vercel, auto-deploys previews on push via GitHub integration
- **No charts.** v1 used Recharts across several pages; v2 deliberately has none — the 5-page scope doesn't need them, and Apple's own Settings/Wallet-adjacent apps lean on numbers, lists, and simple progress bars rather than charts for this kind of everyday-finance surface. The dependency was removed from `package.json`.

## 2. Design system — real Apple HIG, not an approximation

The core instruction was "how Apple would design something like this, one to one copy" — meaning actual HIG values, not a vibe. Supports **both light and dark**, following the system automatically (`prefers-color-scheme`), which is itself more authentically Apple than the several static-dark-only design systems v1 went through.

### Tokens (`app/globals.css`)
- Full systemGray scale (`--gray` … `--gray6`), separate light/dark values.
- Tinted label hierarchy exactly matching Apple's own opacity-based system: `--label` (solid), `--label-secondary` (60% over the label color), `--label-tertiary` (30%), `--label-quaternary` (18%) — not distinct hex approximations.
- Real separator (`rgba` over gray, not a flat hex), system fill tiers, systemBlue/Green/Red/Orange/Purple/Indigo/Teal/Pink at their real light and dark values.
- System font stack (`-apple-system, "SF Pro Text", "SF Pro Display", …`) — no downloaded typeface. Native apps don't ship a custom font either, and this also means every native weight is available for free (a real bug category from an earlier v1 redesign — "does this weight exist in the loaded set" — is structurally impossible now).
- **Money renders in the body font with `tabular-nums`, not a mono font.** SF Mono is for code; real iOS shows currency in tabular SF Pro.
- Full SF text-style ramp as classes: `.ios-large-title` (34/700), `.ios-title2`, `.ios-title3`, `.ios-headline` (17/600), `.ios-body`, `.ios-subhead`, `.ios-footnote`, `.ios-caption`, `.section-header`.

### Material vs. solid
`.glass` is a **solid** grouped-list card (`--bg-elevated`, 14px radius, hairline border) — the real Settings/Health app look. `.material` (blur + saturate) is reserved for **overlay chrome only** — the mobile tab bar, the Quick Add sheet, the date-picker popover — never for content cards. This is the correct HIG distinction; v1 got this wrong on its first Apple-styled pass and had to correct it in a later "deep-detail" pass.

### Components
Real iOS switch (51×31, systemGreen when on), real segmented control (sliding thumb via `data-active`), a bubbly Apple-style date picker (`components/ui/DatePicker.tsx`, portaled calendar popover, carried over unchanged from v1 since it was already correct and has no schema dependency), 10px corner radii on inputs/buttons (rounded rect, not a pill and not architectural), large-title in-content headers (no redundant top app-bar).

### The one rule that has survived every redesign this project has ever done
No color-coding for good/bad beyond real, deliberate use of systemGreen/systemRed for income/expense amounts and destructive actions — direction (↑/↓, +/−) and weight still do most of the signaling work. This is now the sixth-or-so design system this project has shipped; this restraint is the one thing that has survived every single one.

## 3. Data model (Supabase tables)

The biggest structural simplification versus v1: **one unified `entries` table** replaces the old separate `transactions` / `income` / `transfers` / `recurring_bills` / `recurring_income` tables. A `type` column (`'expense' | 'income' | 'transfer'`) distinguishes the three cash-flow directions, and an `is_recurring` flag marks predictable ones — there is no separate cron-driven auto-posting system; recurring items are just entries with a flag, surfaced on the Budgets page with a manual "Log this month" action.

```sql
settings        (id, user_id, currency_code default 'USD', low_balance_threshold, created_at)
accounts        (id, user_id, name, kind 'asset'|'liability', starting_balance, sort_order)
categories      (id, user_id, name, monthly_budget, sort_order)
entries         (id, user_id, date, type, amount, account_id, to_account_id,
                  category_id, description, notes, is_recurring, created_at)
savings_goals   (id, user_id, name, target_amount, target_date, account_id, saved_so_far)
```

Every table has `user_id uuid not null references auth.users(id)` and an RLS policy `using ((select auth.uid()) = user_id)` — the `select`-wrapped form per Supabase's RLS perf guidance, carried over from v1's own hard-won lesson on this.

Two computed views, both `security_invoker = true` so they respect the querying user's RLS automatically:
- `account_balance` — live net worth per account (`starting_balance + income − expenses ± transfers`, liabilities sign-flipped), no manual snapshot/reconciliation step.
- `budget_vs_actual_this_month` — per-category budget vs. actual spend this month.

`handle_new_user()` (a trigger on `auth.users`, `security definer`, RPC access revoked from `public`/`anon`/`authenticated`) auto-provisions every new signup: one settings row, two starter accounts (Checking/Savings), and 8 generic default categories. Signup is fully open — no invite gate, matching v1's later multi-tenant conversion.

Verified via a rollback-only SQL test (the standing discipline on this project): signup provisioning, an expense + income + transfer, a linked savings goal, and both views' math all check out — `begin; ...; rollback;` in one atomic call, zero residue confirmed afterward.

## 4. Pages (6, down from ~27 — originally launched at 5; Assistant added post-launch)

1. **Home (`/`)** — hero net-worth card (live, not a snapshot), this month's spent/income, an account list, recent activity. Quick Add is a floating action button available everywhere. Shows a live-converted secondary-currency line (e.g. `≈ ETB ...`) under each figure when Settings has one configured.
2. **Transactions (`/transactions`)** — the one unified ledger. Filter by type (All/Expense/Income/Transfer), search, inline edit, delete, CSV export.
3. **Budgets (`/budgets`)** — category budgets vs. actual this month (inline-editable budget amounts, a progress bar per category) plus a **Recurring** section listing entries flagged `is_recurring`, each with a one-tap "Log this month" action.
4. **Goals (`/goals`)** — savings goals with progress bars; a goal can either track a real linked account live (`account_balance`) or a manually-entered "saved so far" amount.
5. **Assistant (`/assistant`)** — a read-only AI chat. 6. **Settings (`/settings`)** — accounts (name, asset/liability, starting balance — this is where net worth's components live), categories, main + optional secondary currency code, email + sign out, one-click full data export (JSON).

Auth (`/login`, `/signup`) and `/privacy`/`/terms` are unchanged in structure from v1, just trimmed of references to cut features (MFA, receipt uploads, self-serve account deletion).

## 5. What was cut, and why

Everything below existed in v1 and was deliberately not rebuilt, because it doesn't fit "essentials + a couple extras" at v2's scope: MFA/TOTP, backup & restore, month-end close & period locking, tax-time reporting, forecasting & scenarios, audit log, multi-currency (beyond a single `currency_code` display preference), transfers/weekly-rollup/monthly-rollup/net-worth as their own dedicated pages (net worth folded into Home; transfers folded into the unified ledger), CSV bank import, global search (⌘K), the onboarding modal, email digest/notifications, receipt attachments, PWA install-prompt polish beyond what already existed. The two "couple extras" kept beyond a bare MVP ledger were **net worth** (live, on Home) and **recurring bills/income** (the Recurring section of Budgets) — a judgment call flagged to Abel at plan time since he didn't specify which extras, not overridden since.

`/accounts/[id]` (the old Wallet-card-stack per-account detail page) was also cut — account management lives in Settings now, and Home's account list is a plain list, not a card-stack metaphor (that was specific to the "Apple Wallet" v1 redesign, not this HIG-general one).

## 6. Non-goals (unchanged from v1)
No multi-user sharing/permissions, no bank account sync (Plaid, etc.) — manual entry only, no native mobile app (responsive PWA-feel web app is enough).

    - **UI**: Quick Add's Amount field grows a two-way segmented toggle (main currency / secondary currency) — only rendered when a secondary currency is actually configured in Settings, matching this app's established progressive-disclosure pattern (no dead chrome for the common case of a single-currency user). A live "≈ {main currency amount}" preview appears under the input as you type, computed client-side from the same `fxRate` already fetched for the ETB-everywhere display feature (no extra network call). The Transactions edit row gets the matching currency picker, defaulting to the entry's actual stored currency/figure (`entry_original_amount ?? amount`, not the converted main-currency number, so editing an ETB entry shows you the birr figure you actually typed, not its dollar conversion). Read-only rows with `entry_currency` set show the original logged figure plainly (e.g. "ETB 500.00 logged", no `≈`, since it's the exact recorded amount) instead of a live-reconverted estimate, which would misrepresent what was actually paid if the rate has since moved — entries without a distinct entry currency keep the existing live `≈` conversion unchanged. CSV export gained "Original Currency"/"Original Amount" columns so this information isn't lost on export.
    - `app/(app)/layout.tsx` now fetches `settings` once (main + secondary currency, plus the live rate) and threads it through `AppShell` to `QuickAddFab`, alongside the existing `categories`/`accounts` props.
    - Verified: `tsc --noEmit`/`npm run lint`/`npm run build` all clean (still 14 routes); `get_advisors` (security) clean except the one standing pre-existing item; `generate_typescript_types` re-run and `lib/supabase/database.types.ts` regenerated from the live schema rather than hand-edited, so the new columns are fully type-checked everywhere they're touched.
  - **Low-balance/over-budget nudge on Home, plus bank statement CSV import.** Abel picked both options from a follow-up `AskUserQuestion` round on "what more can we do" — the alert (small, in v2's existing scope) and the CSV import (explicitly reopening a feature deliberately cut when v2 was rebuilt to shrink scope, since Abel picked it knowing that).
    - **Alerts**: `settings.low_balance_threshold` turned out to already exist in the v2 schema (per this file's own §3 data model) but had never been wired to any UI or logic — added a Settings → Alerts card (blank = off) and `updateLowBalanceThreshold()` action, then computed two kinds of quiet nudges on Home: an asset account whose live `account_balance` drops below the threshold, and a budget category whose `budget_vs_actual_this_month.actual_spent` exceeds its `monthly_budget` this month. ## 2. Design system — Liquid Glass Monochrome

**Superseded — see Build Log "Neo-Luxury redesign" below for the current, live design system.** This section is kept as historical record of the original design pass; the app no longer implements it.

Locked in from design pass. Reference build: `command-deck-mono.html` — build the component library to match it exactly, don't reinterpret. (Uploaded to the repo build session; the exact CSS from it is transcribed verbatim into `app/globals.css`.)

**This is NOT generic glassmorphism.** Generic glassmorphism = one flat `backdrop-filter: blur()` on a translucent box. Liquid glass = layered depth (multiple blur/opacity tiers so panels sit at different "densities"), an ambient light source behind the page that glass panels refract (never put the glow on the card itself — put it on the page background), specular top-edge highlights (1px gradient line, not a uniform border), and grain texture so it doesn't read as a flat digital sheet.

### Color tokens
```css
--bg: #08080a;              /* near-black page base, never pure #000 */
--silver: #eceaf0;           /* the one accent — bright numbers, live states */
--silver-dim: #9c9aa5;       /* secondary emphasis, gradient stops */
--text: #f2f1f5;             /* primary text */
--text-dim: #86848f;         /* labels, secondary text */
--text-faint: #48474e;       /* captions, tick marks, disabled */
--glass-border: rgba(255,255,255,0.07);
--glass-border-strong: rgba(255,255,255,0.14);
```
No color-coding for good/bad (no green/red). Monochrome is the whole point — positive/negative and status signal has to come from typography weight, icon direction (↑/↓), and position, not hue. **Resolved in Phase 3**: icon direction + weight + border-strength, no hue. See Build Log.

### Typography
- **Display (headings, section titles):** Clash Display, weight 500–600 — loaded via Fontshare CDN (`api.fontshare.com`), not self-hosted (no font files were provided).
- **Body/UI (labels, copy):** General Sans, weight 400–600 — same Fontshare load.
- **All numbers, everywhere — no exceptions:** IBM Plex Mono, via `next/font/google`. Tabular figures, financial-terminal feel.

### Glass panel spec
```css
.glass{
  background: linear-gradient(155deg, rgba(255,255,255,0.055), rgba(255,255,255,0.012) 40%, rgba(255,255,255,0.025));
  backdrop-filter: blur(20px) saturate(120%);
  border: 1px solid var(--glass-border);
  border-radius: 20px;
}
/* + specular top highlight (::before, 1px gradient line) */
/* + faint corner glow (::after, radial gradient, blurred) */
```
Page background carries 3 layered radial-gradient light sources (top-left, top-right faint, bottom-center) at low opacity. Grain overlay via SVG feTurbulence at ~5% opacity, `mix-blend-mode: overlay`, fixed position.

### Layout
Bento grid, not a uniform card grid — vary panel size by data importance (Current Balance is the largest panel on Command Deck, always). 12-column grid, gap 16px, 20px border-radius on all glass panels.

### Signature element
The Cadet Week progress bar is not a generic progress bar — it's light traveling through liquid glass toward Fall Finals, with an animated sweep highlight (`prefers-reduced-motion` disables the sweep). Reused in Semester Planner.

### What NOT to do
- No color-coded charts/badges (breaks monochrome discipline)
- No flat single-layer blur — always layer at least 2 glass densities per screen
- No pure black backgrounds, no pure white text
- Don't let hierarchy collapse to "everything is silver" — text-dim/text-faint need to be doing real work

## 3. Data model (Supabase tables)

**Ground truth is the real `Expense_Tracker.xlsx`, not this section verbatim** — see Build Log for the corrections that were made (no Payoneer balance account, categories carry a `monthly_budget`, exact enum values, etc.) before writing the actual migration in Phase 2.

```sql
-- Single settings row (fx rate, matriculation date, starting balances)
settings (
  id, fx_rate_etb_per_usd, matriculation_date,
  sofi_starting_balance, ally_starting_balance,
  cash_starting_balance, updated_at
)

categories (
  id, name, monthly_budget, sort_order
)

transactions (
  id, date, cadet_week int,          -- computed on insert from matriculation_date
  category text,                      -- CHECK constraint, 10-value enum, see §4
  description text,
  necessary_or_discretionary text,    -- 'Necessary' | 'Discretionary'
  is_recurring boolean,
  currency text,                      -- 'USD' | 'ETB'
  amount_original numeric,
  amount_usd numeric,                 -- computed at insert time using fx_rate at that date
  payment_method text,
  notes text
)

income (
  id, date, cadet_week int, source text,
  currency text, amount_original numeric, amount_usd numeric, notes text
)

recurring_bills (
  id, name, category, monthly_cost_usd, billing_day, payment_method, active boolean
)

savings_goals (
  id, name, target_amount_usd, target_date, saved_so_far_usd
  -- remaining, % complete, monthly $ needed = computed, not stored
)

net_worth_snapshots (
  id, snapshot_date, sofi_actual, ally_actual, cash_actual, notes
  -- total_actual, computed_balance, variance = computed
)

key_dates (
  id, event, window_label, status, budget_note
  -- "window_label" is free text (e.g. "Late Nov 2026") — most real dates are estimated ranges, not exact ISO dates.
  -- Named window_label, not window, because WINDOW is a reserved word in Postgres.
)
```

**Category enum** (from Monthly Rollup headers, real xlsx order): Mess Hall/Dining, Uniform/Gear/Laundry, Personal Care, Weekend/Leave/Travel, Academic/Books, Transportation, Health/Medical, Tech & Subscriptions, Gifts & Occasions, Other.

**Payment methods** (real xlsx Settings tab): SoFi Debit, Ally, Payoneer, Cash, VMI Cadet Store Charge, Other. Payoneer is a payment method only — it does **not** have its own balance/starting-balance field.

**Income sources** (real xlsx, not a hard constraint — free text with UI suggestions): Family Support, Cadet Pay/Stipend, SoFi/Ally Drawdown.

**Cadet Week logic:** `floor((date - matriculation_date) / 7) + 1`, matching the Weekly Rollup sheet. Dates before matriculation are negative weeks (pre-departure spend).

  1. **Cascade ordering deadlock in `delete_own_account()`.** `transactions.category_id`/`transaction_splits.category_id`/`recurring_bills.category_id` were left `ON DELETE NO ACTION` (the Postgres default) while every sibling `account_id` FK already correctly used `ON DELETE SET NULL`. Fixed by switching all three to `SET NULL`, matching the existing `account_id` convention (`category_fks_set_null_not_no_action` migration).
  2. **`audit_log`'s FK to `auth.users` made every account deletion fail.** `log_audit_change()` fires `AFTER DELETE` on `transactions`/`income`/etc. and inserts a fresh `audit_log` row referencing `old.user_id` — but by the time those cascade-deletes run as part of `delete from auth.users`, the parent row is already gone, so the INSERT violated `audit_log_user_id_fkey`. Fixed by dropping that FK entirely (an audit trail legitimately shouldn't be hard-linked to the live identity of the actor it describes — it already stores full `old_data`/`new_data` snapshots for exactly this reason) and having `delete_own_account()` explicitly purge the caller's `audit_log` rows *after* the cascade, since the cascade itself generates fresh "this was deleted" entries that need cleaning up too, not just the pre-existing ones.
  3. **Supabase's `storage.protect_delete()` guard blocks direct SQL deletes on `storage.objects`.** The first `delete_own_account()` draft tried to clean up the `receipts` bucket via a raw `DELETE FROM storage.objects`; testing surfaced the guard ("Use the Storage API instead").   4. **`post_due_recurring_bills()`/`post_due_recurring_income()` would have silently broken for every user on a day any one user's month was closed.** Both are single `security definer` calls looping over *every* user's due rows with no per-row exception handling; the new period-lock trigger raises on any insert into a closed month, and an uncaught exception inside a plpgsql loop aborts the whole function call — one user closing their current month would have silently skipped everyone else's auto-posting that day too.
